How to resolve effects at comptime

Is there a way to get non-trivial static checks in a programming language without giving in to the siren call of type systems? By “non-trivial checks” I mean any check that can't trivially be done as part of parsing. An example of a trivial check would be checking that variable names can be lexically resolved in the current scope.

Many non-trivial properties can be checked at compile time if you're willing to add a type system. But is there a way to check some interesting properties without adding a full type system, by relying on the evaluation semantics that a language already has, but before the program is actually run? In other words, by using comptime evaluation?

An example of a non-trivial check that I'm interested in is statically checking that effect handlers can be resolved. Let's say I use an effect called as read-file(...)? in a function f somewhere. The entire point of having effect handlers is that the function f that's using the read-file effect doesn't need to care about the implementation of read-file and that read-file isn't even (lexically) bound in f. Instead, a caller of f needs to ensure that read-file is bound to some handler while f is active:

f(name) = {
    file = read-file(name)?
    // do something with the file
}

// f(...) called in a test:
try {
    f("foo.txt")
} [
    [read-file(arg)?, resume] => {
        resume("mock content")
    }
]

// f(...) called as production code:
try {
    f("foo.txt")
} [
    [read-file(arg)?, resume] => {
        // read an actual file, then resume
        // ...
    }
]

A parser can't lexically resolve read-file in f, because the specific handler depends on how f is called. Worse, the definition of f might be separated from the call site of f through multiple intermediate function calls, which shouldn't care about f being effectful. This means that the simplest solution, which would be to simply thread the implementation of read-file through the call stack as an explicit extra argument, is out, because it would require a non-local transformation of large parts of a program. So, what are our options?

Dynamic environment of effects

The simplest solution that doesn't require manual threading of effect handlers is dynamic scope, implemented by (implicitly) threading an extra argument that stores the dynamic environment through all functions, for example as an array of handler implementations indexed by (interned) effect name. A compiler would simply add this extra argument to all function calls and definitions, even if the function in question does not use any effects or call any effectful functions, thus keeping compilation simple. Calling an effect corresponds to looking up the effect name in the environment, handling an effect corresponds to binding the effect name in the environment:

f(env, name) = {
    read-file = resolve(env, "read-file")
    file = read-file(name)
    // do something with the file
}

// f(...) called in a test:
bind((env) => {
    f(env, "foo.txt")
}, "read-file", (arg) => {
    "mock content"
})

// f(...) called as production code:
bind((env) => {
    f(env, "foo.txt")
}, "read-file", (arg) => {
    // read an actual file, then resume
    // ...
})

This is simple, but has a few disadvantages:

  • Every function now needs to thread the environment around, even if the function is pure.
  • Every effect resolution is a lookup, which is slower than just accessing an argument.
  • A missing effect handler is a runtime error, not a compile time check.

As for how to implement the environment, the data structure could either be an array indexed by an interned effect name (in O(1), but with the environment's size determined by the total number of effects in the entire program, regardless of how many of them are bound at any particular time), or a linked list of handler implementations (with a size corresponding to the number of active handlers, but with O(n) lookup due to the need to walk the list).

Comptime specialization

Wouldn't it be nice if we could resolve effects at compile time, thus getting rid of the dynamic lookup overhead? What if instead of threading around an environment at runtime, we instead rely on machinery that binds and resolves variables at comptime? This requires more than just the ability to evaluate some comptime-annotated function calls at compile time, because we need the ability to set the effect bindings during comptime evaluation (in an extra out-of-band data structure that doesn't survive comptime) and specialize even non-comptime-called function bodies so that any effect that is resolved in their body (or any of the functions called in their body) is resolved at comptime through specialization:

f(name) = {
    read-file = resolve!("read-file")
    file = read-file(name)
    // do something with the file
}

// f(...) called in a test:
bind!(() => {
    f("foo.txt")
}, "read-file", (arg) => {
    "mock content"
})

// f(...) called as production code:
bind!(() => {
    f("foo.txt")
}, "read-file", (arg) => {
    // read an actual file
    // ...
})

This is effectively partial evaluation, because we need to resolve bound variables (of effects) in function bodies without calling them. Not only do we need additional comptime machinery for this (specialization and the extra VM data structure for the bound effects at comptime), we also rely on something that can easily lead to non-termination if we naively specialize functions by resolving all variables that can be resolved. We could try to restrict the specialization to only what we need for effects (for example by only substituting variables that resolve to values, never if they remain deferred computations with variables in them), but partial evaluation remains far from trivial.

Desugaring effects where they are mentioned

Another option, still fully at comptime, is to track the effect signature of each function. This normally requires a relatively sophisticated type system (well, effect system) because of cases like the following:

f(name) = {
    file = read-file(name)?
    // do something with the file
}

// note how f is an effectful function here:
map(f, ["foo.txt", "bar.txt"])

It's easy enough to say that the definition of f requires the effect read-file, but what about the definition of map? If we call map with a function like f that expects an effect handler for read-file, the call map(f, ["foo.txt", "bar.txt"]) will only be valid if the effect read-file is required here. But if f doesn't require an effect, then neither does map(f, ["foo.txt", "bar.txt"]). In other words, map is effect polymorphic and we need an effect system that can express this polymorphism for map.

At least that's the usual story. But is there a simpler alternative? What if we simply require all first-class functions (including map's parameter f) to be fully bound with effect handlers at the site where they are mentioned? Inside map, the parameter f would then always be a fully effect-bound function and map never has to care where the effect binding comes from, because the effect binding must be in scope when the argument is passed to map.

f(name) = {
    file = read-file(name)?
    // do something with the file
}

f_with_effect = bind(f, "read-file", (arg) => {
    "mock content"
})

map(f_with_effect, ["foo.txt", "bar.txt"])

Under the hood, all effectful functions (and transitively their callers) are rewritten by the compiler to pass one additional argument per effect. This doesn't require any additional machinery in the VM, but it makes the compiler more complicated, because it now has to implement a (fully inferred) effect system that desugars to normal parameter passing.

Another disadvantage is that effect bindings must be statically observable by the compiler, meaning bind(f, "read-file", ...) has to explicitly name the read-file effect, it cannot come from a variable (or we would have to resolve variables at comptime), making effect names second-class citizens in the language.

One detail worth noting is that comptime specialization and desugaring effects where they are mentioned lead to different semantics in the case of nested effect handlers such as the following snippet that binds the log effect to either log to the console or to a file:

bind(() => {
    task = () => {
        // the log effect is _mentioned_ here:
        log("hello")?
    }
    bind(() => {
        // the log effect is _called_ here:
        task()
    }, "log", (arg) => {
        // log to file
    })
}, "log", (arg) => {
    // log to console
})

Does the call log("hello")? log to the console or to a file? With comptime specialization, it would log to a file, because at the point where task() is called (and comptime-specialized) the active implementation is // log to file. But if effect handlers are resolved where effects are mentioned, then the handlers already gets resolved within task = () => { ... } where the log is first mentioned and thus logs to the console.

Comptime specialization for dynamic environments

What if we combined comptime specialization with a dynamic environment parameter? We would then still pass around an environment as part of every function call, but this is cheap if we pass it by reference. The more expensive part, looking up the effect handler, would be specialized away by being bound and resolved at comptime. This would have two advantages: First of all, there's no need for an extra data structure in the VM, because the environment is simply a normal function parameter. Second, we can choose whether to resolve an effect at comptime or at runtime: If the effect call is comptime-annotated, the resolution fails at comptime if the environment does not contain the handler. If the resolution is just a regular call, it will be resolved at runtime and fails if there's no effect with the given name in scope. Dynamic scope, optionally resolved at comptime.

Would this hit a sweet spot? The only new machinery is specialization for bound values (anything that is not fully evaluated to a value remains deferred) and the error messages remain good because a comptime-annotated resolution fails at comptime at the effect call site. But patterns that require runtime resolution of effects (such as storing effect handlers or effectful functions in data structures as callbacks) remain possible.

One thing to note though is that giving up dynamic effect resolution and relying fully on either comptime specialization or mention-is-resolution might be a smaller loss than it might initially appear, because effect resolution at compile time only implies that the name must be bound and resolved at compile time, while the specific value of the effect handler can still rely on runtime values. An effect could thus resolve to a handler that simply picks a concrete handler implementation out of a list based on a runtime list index.

Tail resumption, one-shot resumption

One aspect glossed over in the above discussion of how to resolve an effect is how resuming an effect call site actually works, including for non-resuming effect handlers, which are how effect handlers can model control flow constructs. After all, effect handlers are not simply functions, because they might not resume, or resume with the call stack wrapped in an expression (such as foobar(resume(...)), which wraps the result of resuming the effect in foobar(...)), or even resume multiple times if multi-shot continuations are supported.

We can categorize effect handlers roughly based on how they resume a continuation:

  • Tail resumption, effectively function calls
  • Aborting handlers where resume is never called
  • Tail resumption while also binding state to a new value
  • Non-tail resumption or multi-shot resumptions

Luckily, most effect handlers seem to fall in the first three categories (or a combination of them, such as either tail-resuming or aborting based on an if statement), which do not require fully reified stacks but only normal function calls (for tail resumption) or a single extra VM instruction to unwind the stack (for aborts).

Resuming and rebinding state to a new value is common enough that machinery for such state can be made part of how handlers work, which is how Koka seems to work. A reified call stack that can be passed around and potentially resumed multiple times is then only necessary for handlers of the last category. But such handlers seem to be rare in practice, perhaps it's sufficient to simply not support these resumption patterns?
